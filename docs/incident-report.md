# SOC Incident Report: Simulated Path Traversal

## 1. Case Information

| Field | Details |
|---|---|
| Case ID | SOC-LAB-001 |
| Incident type | Suspected path traversal / unauthorized file access |
| Environment | AWS EC2 Ubuntu test application |
| Detection platform | Wazuh Cloud |
| Detection rule | 100501 |
| Severity | Level 10, as configured in the lab |
| Classification | Confirmed lab simulation; not a real-world attack |
| Analyst | Project author |
| Date | 27 October 2026 |

## 2. Executive Summary

A controlled path traversal test was performed against a deliberately vulnerable Python web application hosted on an AWS EC2 Ubuntu instance. The test attempted to read a synthetic file outside the application's intended web root.

The application returned HTTP 200 and logged the request. The Wazuh agent collected the application's JSON log, and Wazuh Cloud generated an alert using custom rule 100501.

The test demonstrates end-to-end application log collection and custom detection. Because the request was generated by the analyst, the event is classified as a simulated security incident rather than a real attack.

## 4. Investigation and Evidence

### Evidence 1 — Application access log

The application recorded the request in JSON format with the request path, client address, HTTP status, event type, timestamp, and user agent.

The `status` value was `200`, indicating that the application reported a successful response.

### Evidence 2 — Wazuh alert

Wazuh Cloud displayed the event with custom rule ID `100501`. The alert's `full_log` contained the original JSON record, and the JSON decoder exposed fields such as `data.request`, `data.status`, and `data.event`.

This confirms that the application log was collected, decoded, and matched by the custom rule.

### Evidence 3 — Controlled reproduction

The analyst issued a test request from their own laptop. The application returned the contents of a synthetic test file outside its intended web root.

No real credentials were used.

## 5. Technical Analysis

The request used a traversal sequence (`..%2f`) to attempt to navigate outside the application's intended directory.

The application was deliberately configured without adequate path confinement. As a result, the requested file could be read.

The custom Wazuh rule matched the observed request pattern and generated an alert. This rule is specific to the lab's test pattern; it does not detect every possible traversal encoding or prove malicious intent.

## 6. MITRE ATT&CK Mapping

**Potential technique:** T1190 — Exploit Public-Facing Application.

This is a possible contextual mapping because the test exploited a vulnerable web application. The mapping should be treated as provisional: a path traversal vulnerability does not automatically establish that a specific ATT&CK technique applies in every scenario.

## 7. Impact Assessment

- **Confidentiality:** The synthetic test file was readable outside the intended web root.
- **Integrity:** No modification was demonstrated by this test.
- **Availability:** No availability impact was observed.
- **Production impact:** None; this was a controlled lab simulation.

## 8. Recommended Remediation

1. Resolve requested paths to canonical filesystem paths.
2. Reject any resolved path that is outside the permitted web root.
3. Run the application with least privilege and grant access only to required files.
4. Keep sensitive files outside directories accessible to the application.
5. Retain structured application logs and monitor suspicious traversal patterns.
6. Test legitimate requests and multiple traversal encodings before deploying detection rules in production.

## 9. Conclusion

The controlled test successfully demonstrated path traversal against the lab application and confirmed that Wazuh Cloud generated an alert from the application's JSON log.

The lab validates a basic cloud-based detection workflow. The next improvement is to correlate web application events with Linux audit records and test the detection against both benign and suspicious requests.
